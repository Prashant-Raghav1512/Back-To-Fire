# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Born to Fire — a calisthenics/home-fitness marketing site for India (React + TypeScript + Vite + Tailwind), deployed as a **fully static site to GitHub Pages** with **no backend server of any kind**. Every dynamic feature (database reads/writes, AI chat) either happens at build time or talks to a third-party service directly from the browser — there is deliberately no API layer. Live at https://prashant-raghav1512.github.io/Back-To-Fire/, repo at github.com/Prashant-Raghav1512/Back-To-Fire.

## Commands

- `npm run dev` — start the Vite dev server
- `npm run build` — production build; automatically runs `prebuild` (Neon → JSON sync) and `postbuild` (404.html generation), see Architecture below
- `npm run typecheck` — `tsc --noEmit`, the only type-checking command
- `npm run lint` — ESLint
- `npm run preview` — serve the built `dist/` locally
- `npm run fetch-content` — manually re-run the Neon → JSON sync without doing a full build

There is no test suite in this repo.

## Architecture

### No backend, by design

This project was migrated off an earlier Vercel-serverless-functions setup specifically to keep everything on GitHub (`@supabase/supabase-js` in `package.json` is unused leftover from the original scaffold — nothing imports it). The result is two very different patterns for talking to Neon Postgres, and it matters not to conflate them:

1. **Build-time, secure** (`DATABASE_URL`): `scripts/fetch-content.mjs` runs before every build via the `prebuild` script, reads `exercises`/`programs` from Neon using `@neondatabase/serverless`'s HTTP driver (not the WebSocket `Client` — GitHub Actions' runner has no global `WebSocket`), and writes the result to `src/data/exercises.json` / `programs.json`. Those generated JSON files are committed to the repo and imported by `src/data/content.ts`. If `DATABASE_URL` isn't set, the script no-ops and the build uses whatever JSON is already checked in. **`DATABASE_URL` is never shipped to the browser.**

2. **Browser-time, deliberately insecure** (`VITE_NEON_CONTACT_URL`, `VITE_GROQ_API_KEY`): the contact form (`src/lib/contact.ts`) and the AI chatbot (`src/lib/groqChat.ts`) call Neon and Groq *directly from client-side JS*, so both credentials ship in the public bundle. This was investigated, not overlooked: Neon's connection proxy only authenticates roles created through its own control plane, and every such role is automatically added to `neon_superuser` (full read/write/DDL on the whole database), with no way for this project's owner role to strip that membership — there is no scoped/insert-only Neon role possible on this project. The contact form uses a dedicated `contact_public` role (separate from the build-time role) purely so it can be rotated independently if abused, not because it's actually restricted. Read the comments at the top of `contact.ts` and `groqChat.ts` before treating this as a bug to fix.

### GitHub Pages routing (fragile — verify all three cases below after touching it)

GitHub Pages serves this repo at `/Back-To-Fire/`, not the domain root, and there's no server-side routing. Two mechanisms make client-side routing work, both required together:

- `src/lib/router.tsx` reads Vite's `import.meta.env.BASE_URL` and strips/re-adds it when translating between the app's internal paths (`/contact`) and the real browser path (`/Back-To-Fire/contact`). `vite.config.ts` sets `base` from a `VITE_BASE_PATH` env var that the deploy workflow computes from the repo name at build time.
- `scripts/copy-404.mjs` (the `postbuild` script) copies `dist/index.html` to `dist/404.html`. GitHub Pages serves that file (still with an HTTP 404 status) for any unmatched path — this is what makes a direct load or refresh on `/contact` work instead of hitting GitHub's own generic 404 page.

These broke independently before (commit `e2fe407`). After any change to routing, the `base` config, or the build scripts, check: a fresh direct load of a non-home route, a page refresh on a non-home route, and a client-side nav-link click.

### Route-based code splitting

`App.tsx`'s `Routes` component `React.lazy()`-loads every page **except** `HomePage`, which stays a static top-level import since it's the page most visits land on and eagerly bundling it avoids a loading flash on the single most common first paint. Every other page (`AboutPage`, `ProgramsPage`, `CommunityPage`, etc.) is wrapped as `lazy(() => import('@/pages/XPage').then((m) => ({ default: m.XPage })))` — the `.then` adapter exists because these are named exports, not default exports, and `React.lazy` requires a default export. The whole `<Suspense fallback={<PageLoadingFallback />}>` boundary wraps just the routed `page` inside `<main>`, not `Navbar`/`Footer`/`ChatWidget` — those stay always-mounted. Before this, the entire app (chatbot, community, membership, translator, every page) shipped as one ~950KB JS chunk regardless of which page a visitor opened; splitting brought the initial bundle down to ~490KB (~150KB gzipped) with the rest loaded on demand per route. If you add a new page, lazy-load it the same way unless there's a specific reason it needs to be in the initial bundle.

### Performance & security hardening

A few changes exist purely to fix real, measured issues (via Lighthouse against the live site), not for their own sake:

- **CSP via `<meta>` in `index.html`.** GitHub Pages can't set real HTTP response headers at all, so a `<meta http-equiv="Content-Security-Policy">` tag is the only header-adjacent protection available — it can't cover `frame-ancestors` (silently ignored in a meta tag per spec, HTTP-header-only). Origins are scoped to exactly what this app talks to (Clerk, including its `clerk-telemetry.com` telemetry endpoint, Neon, Groq, Google Translate, Google Fonts); `'unsafe-inline'` stays on `script-src`/`style-src` because Clerk's embedded widget injects both at runtime, and blocking it would break sign-in outright. `media-src` explicitly repeats `img-src`'s `data:`/`blob:` allowance — without it, `<video>`/`<audio>` silently falls back to `default-src 'self'` and blocks the `data:` URIs Community posts store videos as (`src/lib/videoUpload.ts`), a real bug this project shipped once already. If you add a new third-party origin, or a new media/fetch directive anywhere in the app, it needs adding here too or that feature will silently fail (CSP violations don't throw catchable JS errors, they just block the request) — test the actual feature after touching this, don't just eyeball the policy string.
- **Google Fonts via `<link rel="preconnect">` + `<link rel="stylesheet">` in `index.html`, not a CSS `@import`** in `index.css`. `@import` forces the browser to fully fetch and parse the app's own stylesheet before it can even discover the font stylesheet URL — a full extra network round-trip before font loading starts.
- **The hero/testimonial/logo JPEGs are compressed** (mozjpeg re-encode at quality 72, `logo.png` resized to match its actual ~40px display size). If you ever swap any of these images, re-compress before committing — there's no build-time image optimization step, whatever's in `public/` ships as-is.
- **The Home page showcase video is lazy-mounted**, not just lazy-loaded: `HomePage.tsx` doesn't render the `<video>` element at all (via `videoInView` state) until an `IntersectionObserver` on its wrapper fires, so the browser's speculative preloader never sees the 2.7MB `btf-showcase.mp4` URL in the initial HTML/DOM despite `autoPlay` — this used to start fetching immediately on every Home load regardless of whether the visitor ever scrolled to that section.
- **`favicon` is `logo.png`**, not a `vite.svg` — the scaffold's default favicon reference was never updated after the real logo was added, which meant every single page load threw a real 404 in the console (Lighthouse's Best Practices score flagged this directly).

### Content model

`src/data/types.ts` defines the `Exercise`/`Program`/`FitnessEvent` shapes. `src/data/content.ts` re-exports those types plus the Neon-sourced `exercises`/`programs` arrays (from the generated JSON — see above) and two purely static arrays, `benefits` and `navLinks`, that are not Neon-backed. `db/schema.sql` is the source of truth for the Neon schema (`programs`, `exercises`, `contact_submissions`, `enrollments` tables) — it's an idempotent create+seed script, safe to run against a fresh database.

### Events

`src/data/events.ts` is a hand-maintained static array (`events`), following the `benefits`/`navLinks` pattern above, not Neon-backed — add/edit events by hand in that file. Critically, **status (`upcoming`/`ongoing`/`ended`) is never stored**, only `startDate`/`endDate`; `src/lib/events.ts`'s `getEventStatus` derives it by comparing against `new Date()` at render time, so it's never possible for a displayed status to drift out of sync with reality. Each event also carries an `agenda` (ordered `EventAgendaItem[]`, each with its own `date`/optional `time`) and an optional `recap` string. Events live on the same page as Programs — see "Programs & Events page merge" below — which groups them into three sections via `groupEventsByStatus`; `HomePage.tsx` shows a 3-event spotlight (ongoing + soonest upcoming). Every event card opens `src/components/EventModal.tsx`, which shows "What happened" + the `recap` for ended events, "What to expect" (the full agenda) for upcoming events, or — for ongoing events — the agenda split into "what's happened so far" vs. "what's coming up next" via `getAgendaItemStatus`, which resolves each item's own `date`+`time` against `now`. Expressing interest in an ongoing/upcoming event uses the same `EnrollButton` described in "Enrollments" below.

### Programs & Events page merge

`/programs` and `/events` used to be two separate pages/routes; they're now one — `src/pages/ProgramsPage.tsx` holds program cards, the three event sections (Happening now / Coming up / Past events, unchanged from the old `EventsPage.tsx`), the paid membership plans, the gym branch locator, and the "how it works" explainer, in that order. **Both routes still resolve** (`App.tsx`'s switch has `case '/programs': case '/events':` falling through to the same component) so any existing links/bookmarks to `/events` keep working — there's no redirect, both URLs just render the same page. `navLinks` (`src/data/content.ts`) has a single `"Programs & Events"` entry pointing at `/programs`; there's no separate `Events` nav item anymore. If you're looking for `EventsPage.tsx`, `EventCard`, or `EventGrid` — they're inside `ProgramsPage.tsx` now, not a separate file.

### Enrollments

Signed-in users can enroll in a program (`src/pages/ProgramsPage.tsx`'s "Start" buttons) or an event (`EnrollButton` in the same file's `EventCard`, or in `EventModal.tsx`) — this writes a row to Neon's `enrollments` table, it does **not** redirect to the contact form. `src/lib/enrollments.ts` holds the browser-side `enroll()`/`getMyEnrollments()` functions and the `useMyEnrollments()` hook (fetches the signed-in user's rows once per page, exposes `isEnrolledIn(type, id)` and a `refresh()` to call after a new enrollment). `src/components/EnrollButton.tsx` is the one shared button used everywhere enrollment happens — it owns the sign-in gate, the in-flight/enrolled/error states, and calls `onEnrolled` (always a `refresh()` from the hook) on success. `src/pages/ProfilePage.tsx` (route `/profile`, reachable from the "My Profile" item in the `<UserButton>` menu in `Navbar.tsx` — deliberately not in `navLinks`, since it's account-scoped, not marketing nav) opens with a "Personal Details" section (`src/components/ProfileDetailsForm.tsx` — state/age/height/weight/gender, backed by the `community_profiles` table also used by the Community page; name and profile photo are left to Clerk’s own account modal rather than rebuilt here) above "My Programs", "My Events", and "My Posts" (see "Community" below), which list everything the signed-in user has joined or posted.

`enrollments` rows are keyed by `clerk_user_id` (Clerk's user id — there's no `users` table in Neon, since accounts live in Clerk, not this database) plus a snapshot of `item_title`/`item_detail` taken at enrollment time, so a user's history still reads sensibly even if a program/event is later edited or removed from `src/data/*`. Enrollment writes/reads reuse the same browser-exposed `VITE_NEON_CONTACT_URL` connection as the contact form, rather than a new dedicated credential — see the comment at the top of `enrollments.ts` for why (short version: every Neon role on this project is already `neon_superuser` regardless, and provisioning a genuinely new role requires the Neon dashboard/API, which this environment has no credentials for).

### Community

`src/pages/CommunityPage.tsx` (route `/community`, in `navLinks`) is a full page, not the floating bubble it used to be (`CommunityWidget.tsx`/`CommunityBoard.tsx` were removed once the feature outgrew a small panel) — a groups sidebar on the left, a live chat + posts feed for whichever group is selected on the right. Groups come in five types (`CommunityGroupType` in `src/data/types.ts`): `india` (one fixed nationwide room), `state` (all 36 from `src/data/indianStates.ts`), `age` (reuses `ageGroups` from `src/data/paidPlans.ts` — same youth/adults/seniors bands as the paid plans, not a second taxonomy), `interest` (`src/data/communityInterests.ts`, hand-maintained), and `event` (auto-derived from ongoing/upcoming rows in `src/data/events.ts`, so a group never outlives its event). `src/lib/communityGroups.ts` is the single catalog all of these are read from. **`india` is a fully separate room from every state, not an aggregate view over them** — each group’s messages/posts are isolated by `(group_type, group_key)` in Neon, so posting to "All India" doesn’t leak into or out of any state’s room.

Two feeds per group, both scoped to `(group_type, group_key)`: a live chat (`src/lib/community.ts`’s `community_messages` table, `GroupChat.tsx`, polls every 7s) and a slower posts feed (`src/lib/communityPosts.ts`’s `community_posts`/`community_post_comments` tables, `GroupPosts.tsx`, polls every 15s) plus threaded comments (`CommentsModal.tsx`, shared between the Community page and Profile’s "My Posts" section). Posts are never seeded with placeholder content — the feed only ever shows what real signed-in members have posted.

**Media is split by poll frequency, not by feature parity.** Chat supports text and/or one optional photo per message (`community_messages.image_url`); posts support text and/or one optional photo *or* video per post (`community_posts.image_url`/`video_url`, mutually exclusive — the composer clears one when the other is picked, not a DB constraint). Video is deliberately posts-only: chat re-polls its *entire* message history every 7s, so any large inline media there gets re-downloaded by every open chat window every 7 seconds, whereas posts poll every 15s and are a browse-when-you-open-it feed, not a live one — the tradeoff is spelled out in `db/schema.sql`’s `community_messages` comment. A photo (either surface) is compressed/downscaled entirely client-side (`src/lib/imageUpload.ts`, canvas-based, capped around ~900KB of base64). A video (posts only) has no equivalent compression step — no ffmpeg.wasm or similar exists in this stack — so `src/lib/videoUpload.ts` only enforces a hard ~8MB input-size gate before base64-encoding it as-is; video rows can therefore be meaningfully heavier than image rows. Both media types are stored inline as a data URI rather than in real object storage — there’s no backend to sign an S3/Cloudinary-style upload with and no credentials for a third-party host either, so, like `VITE_NEON_CONTACT_URL`/`VITE_GROQ_API_KEY`, they ship straight from the browser (see "No backend, by design" above). Deleting a post or comment is scoped to `clerk_user_id` in the DELETE statement itself, same defensive-not-real-security pattern as the rest of this app’s Neon writes.

**Cold-start empty states.** A group with no messages/posts yet doesn't just show a flat gray sentence — `GroupChat.tsx`/`GroupPosts.tsx` render a centered icon + heading + inviting subcopy ("X is quiet for now" / "No posts in X yet") so an empty group reads as an opportunity to be first, not as a dead feature. Separately, the Community page's hero shows a real, live "N people have joined Born to Fire" stat via `useMemberCount()` (`src/lib/friendId.ts`, a `SELECT count(*) FROM user_ids`) — deliberately a registration count, not an activity count, so it stays honest and meaningful even on a freshly-launched deployment where every group's feed is still empty. This does **not** relax the "never seed placeholder content" rule above — it's a real aggregate of real signed-in visitors, not fabricated content.

**Friends & DMs.** `src/lib/friends.ts` holds the whole relationship model in one table, `friend_requests` (`db/schema.sql`) — a row's `status` (`pending`/`accepted`/`declined`) plus who's `requester_*` vs `recipient_*` covers a request, a friendship, and a declined request all at once, with no separate `friends` table (an accepted row *is* the friendship). A direction-independent unique index (`LEAST`/`GREATEST` over both user ids) guarantees exactly one row can ever exist per pair, which is what `sendFriendRequest` leans on: requesting someone who already requested you auto-accepts instead of duplicating, and re-requesting after a decline flips the existing row back to pending rather than inserting a second one. `useFriends()` fetches every row involving the signed-in user once and derives `friends`/`incoming`/`outgoing` plus a `statusFor(otherUserId)` lookup client-side, so `FriendActionButton.tsx` (rendered next to a message author in `GroupChat.tsx` and a post author in `GroupPosts.tsx`) never needs its own per-author fetch. `src/lib/directMessages.ts`’s `direct_messages` table is a separate, unrelated table (no FK to `friend_requests`) — unfriending (`removeFriend`) deletes the friendship row but deliberately leaves DM history intact, same as most real chat apps. `CommunityPage.tsx`’s sidebar gained a "Direct Messages" section (signed-in only) above the groups list: a "Friend Requests" row (`FriendRequestsPanel.tsx` — search-by-Friend-ID plus accept/decline incoming, cancel outgoing) plus one row per accepted friend, each opening `DirectMessageChat.tsx` — a private 1:1 thread scoped to exactly two user ids rather than a `(group_type, group_key)` room.

**Friend IDs.** `src/lib/friendId.ts`'s `user_ids` table (`db/schema.sql`) gives *every* signed-in visitor a unique, human-shareable ID (e.g. `BTF-U000123`, a `GENERATED` column off the row's own `bigserial` id — same technique as `memberships.member_id` in "Membership" below, but with a distinct `BTF-U` prefix so the two id schemes are never visually confused) — deliberately not gated behind joining a paid membership the way `membership.ts`'s `findMemberByMemberId`/Member ID is. Unlike a `community_profiles` row (only created by saving Personal Details) or a `memberships` row (only created by joining), a `user_ids` row needs no deliberate user action: `getOrCreateFriendId(clerkUserId, displayName)` upserts it silently, refreshing `display_name` on every call rather than snapshotting it once. `FriendIdBootstrap.tsx` calls this via the `useFriendId()` hook and is mounted app-wide in `App.tsx` (same pattern as `ChatWidget`, outside the route switch) purely so the row exists as early as possible after any signed-in page load, not only once someone happens to open Profile or Community. `ProfilePage.tsx`'s hero shows the signed-in user's own Friend ID as a copy-to-clipboard pill; `findUserByFriendId(id)` is the lookup `FriendRequestsPanel.tsx`'s "Add by Friend ID" search box uses to find someone and call the same `sendFriendRequest` every other friend-adding entry point in the app uses.

### Paid membership plans & gym branches

`src/data/paidPlans.ts` (`ageGroups` + `paidPlans`, not Neon-backed) defines paid coaching memberships — a separate concept from the free `programs` in `content.ts`. Three age groups (`youth`/`adults`/`seniors`) each have exactly three tiers (Basic/Standard/Premium); every tier includes calisthenics lessons, gym branch access, and a diet plan, and **only Premium** sets `hasPersonalTrainer: true` — that split is a deliberate product decision (see the comment on `PaidPlan` in `types.ts`), not something to "fix" by adding a trainer elsewhere. `src/components/MembershipPlans.tsx` (rendered on `/programs`, below the free programs) is an age-group tab switcher over these plans; it reuses the same `EnrollButton`/`useMyEnrollments` machinery as free programs, with `itemType: 'program'` — paid plans are stored in the same `enrollments` table via the plan's `id`, no schema change needed, since "enrolling" just registers interest the same way it does everywhere else on this backend-less site (there's no real payment flow).

**The "Pay with" section on each plan is a payment *method selector*, not a real checkout — deliberately.** No payment gateway has been chosen yet, and this site has no backend to safely process one anyway (collecting raw card details client-side with nowhere secure to send them would be a real security problem, not just a missing feature). `src/data/paymentMethods.ts` lists the option set (UPI/Card/Net Banking/Wallet — presentational only, IDs only, no processing logic) and `src/components/PaymentMethodSelector.tsx` renders them as a toggle grid. `MembershipPlans.tsx` requires a method to be picked before `EnrollButton` becomes clickable (via `EnrollButton`'s `disabled` prop — only gates the *already-signed-in* path, so a signed-out visitor can still click through to sign in before picking a method) and appends the choice into the enrollment's `itemDetail` snapshot (e.g. `"... · Pay via UPI"`) so it's at least recorded as a stated preference, not purely cosmetic. When a real gateway is picked, the natural integration point for a backend-less site is hosted payment links (Razorpay/Stripe/etc. host the actual checkout page; this component would redirect/link to it) — not a custom form here.

`src/data/gymBranches.ts` is a static list of branch locations (locality-level lat/lng, good enough for "which is closest," not survey-grade). `src/lib/gymBranches.ts`'s `useNearestBranches()` hook sorts them by distance from the browser's own Geolocation API (Haversine formula, no backend) once the visitor opts in via `locate()`; `src/components/GymBranchLocator.tsx` (also on `/programs`) renders the list and flags the nearest one once located.

### Membership (`/membership`) — not the same thing as "paid membership plans" above

**Naming collision, read carefully:** the "paid membership plans" section above (`paidPlans.ts`, Basic/Standard/Premium per age group) and this feature are two genuinely different, unrelated concepts that happen to both use the word "membership." This one is about *who* a membership covers and *identifying* a member, not which training tier they get.

`src/data/membershipTypes.ts` defines three membership types — `normal` (individual, ₹499/mo or ₹4,999/yr), `corporate` (a company sponsors its team, captures a `companyName`, custom/negotiated pricing so `price`/`yearlyPrice` are both `null`), `family` (covers up to 4 people, ₹1,299/mo or ₹12,999/yr) — plus `sharedMemberBenefits`, a list every member gets regardless of type, and each type's own additional benefits. **Normal and Family are paid, and both offer monthly or yearly billing**: `MembershipPage.tsx`'s `BillingCycleToggle` (Monthly/Yearly, "2 months free" badge) sits above the type picker and drives which of `price`/`yearlyPrice` every card, the confirmation panel, and the eventual `createMembership` call use — `yearlyPrice` is a genuine discounted total, not `price * 12`, so the picker also shows a "Save ₹X" line per card once yearly is selected. Once a type is selected, a priced type must have a `PaymentMethodSelector` option chosen (reusing the same component `MembershipPlans.tsx` uses on `/programs`) before the "Join" button enables — Corporate skips both the cycle toggle's effect and the payment step entirely, just asking for a company name, with copy noting the team reaches out to discuss pricing. None of this is a real charge, same "no backend to safely process a real checkout" reasoning as the paid plans above — the chosen price/payment method are just snapshotted onto the `memberships` row as a recorded preference. That row's price column is still named `monthly_price` in `db/schema.sql` (kept as-is rather than migrated to avoid a rename) but no longer always holds a monthly figure — it's whatever `billingCycle` was chosen, which is why `src/lib/membership.ts` maps it to the TS field `price`, not `monthlyPrice`; a sibling `billing_cycle` column (`'monthly' | 'yearly'`, both nullable — null only for corporate) records which. There's no flow to switch an existing membership's cycle or type — same as switching type, that means cancel and rejoin. `src/lib/membership.ts`'s `memberships` table (`db/schema.sql`) is keyed one-per-`clerk_user_id`; its `member_id` (e.g. `BTF000042`) is a Postgres `GENERATED ALWAYS AS` column derived from the row's own `id`, not a separately issued value, so uniqueness needs no extra coordination. **Only joining a membership grants a Member ID** — browsing the site, or even having a `community_profiles` row, does not; that's deliberate, an ID is meant to read as an actual membership perk.

Two features build on that ID: `family_members` (name/relation/age rows under a `family`-type membership, capped at 4 — enforced in `addFamilyMember` by counting existing rows before inserting, not a DB constraint, same "app-level guardrail" pattern used everywhere else in this backend-less app) and `findMemberByMemberId` — a search-by-ID lookup on `MembershipPage.tsx` that lets a member find another member and send them a friend request via the *existing* Community friend system (`src/lib/friends.ts`), a second way to meet people beyond stumbling into them in a group's chat/posts. The "members-only Community group" benefit is a real gated group, not just copy: `CommunityGroupType` (`src/data/types.ts`) has a `'members'` variant, `communityGroups.ts` exports a single fixed `MEMBERS_GROUP`, and `CommunityPage.tsx`'s sidebar only renders it when `useMembership()` returns a membership — a signed-in non-member never sees it in their group list. `ProfilePage.tsx` has a compact "My Membership" section (the card summary + a "Manage" link to `/membership`, or a join CTA if the user has none) alongside its other "My ..." sections.

### Invoice downloads

`src/lib/invoice.ts`'s `downloadInvoicePdf()` generates a receipt-styled PDF entirely client-side via `jsPDF` (no backend, same constraint as everything else in this app) and triggers a browser download — `src/components/InvoiceButton.tsx` is the one shared button used everywhere it appears. Since there's no real payment gateway anywhere on this site (see "Membership" and "Paid membership plans" above), the PDF is explicit about that in its footer rather than implying a processed charge — it's framed as a record of the plan/price/payment-method preference already stored in Neon, not a transaction receipt. Two entry points: `MembershipPage.tsx` shows it on the member card whenever `membership.monthlyPrice !== null` (Normal/Family — Corporate has no fixed price to invoice), reading the real `monthly_price`/`payment_method` columns directly; `ProfilePage.tsx`'s `ProgramEnrollmentCard` shows it only for enrollments whose `itemId` matches a `paidPlans` entry (free `programs` enrollments have no price, so no button). Unlike memberships, program/event enrollments have no numeric price column at all (`item_detail` is the only place a price ever lands, as free text — see "Enrollments" above) — the invoice's amount comes from re-looking-up `paidPlans.find(p => p.id === itemId).price` (today's listed price, not necessarily what a since-changed plan cost at enrollment time), and the payment method is regex-extracted back out of `itemDetail`'s `"... · Pay via X"` suffix, which is safe only because this same codebase (`MembershipPlans.tsx`) controls that exact string format. jsPDF's core (~130KB gzipped) lands in whichever lazy route chunk imports `invoice.ts` (currently `/profile` and `/membership`, via the route-based code splitting described above) — it does not touch the initial bundle. jsPDF also ships an optional HTML-to-canvas plugin (`html2canvas`/`dompurify`, dynamically imported); this app never calls that code path, and bundlers correctly split it into its own never-fetched chunk — don't be alarmed seeing it in a build size report.

### Chatbot: client-side RAG, no server, global floating widget

`src/lib/search.ts` is a from-scratch BM25 implementation (no external dependency) indexing `src/data/knowledgeBase.ts`. Most of that array is hand-written chunks, not auto-derived from `content.ts` — **except** the event chunks, which are the one deliberate exception: `knowledgeBase.ts` appends `getEventKnowledgeChunks()` from `src/lib/events.ts` at module load, because a hand-written "this event is upcoming" sentence would silently go stale the instant the event started or ended. If you add a new hand-written chunk, it goes in the `staticKnowledgeBase` array, not near the event-chunk logic. `src/lib/groqChat.ts` takes the top-3 BM25 matches for a user's message and feeds them as context to Groq's chat completions API (`llama-3.3-70b-versatile`) with a system prompt instructing it to answer only from that context and admit when it doesn't know; the prompt also names the persona (`Uncle Baiyanpuria`) so the model answers consistently if asked its name.

The bot is split into two components on purpose: `src/components/ChatBot.tsx` is body-only (message list, suggestions, input — no header, no card chrome, fills `h-full` of whatever contains it) and keeps conversation history client-side, replaying recent turns to Groq so follow-up questions work; `src/components/ChatWidget.tsx` owns the floating bubble, the small window frame, and the header (name/"Online now"/close button), and is mounted once in `App.tsx` **outside** the route switch, so its open/closed state and message history persist across client-side page navigation instead of resetting per page — this is what makes it "appear on every page" rather than being embedded once on Contact like before. The opening message is hardcoded to start with "RAM RAM BHAI SAREYANE" — don't move that into the BM25-driven/Groq-generated reply path, it's a fixed local greeting shown before any API call happens. The BM25 tuning (title-term weighting via `TITLE_WEIGHT`, light stemming, the `MIN_MATCH_RATIO` filter) exists to fix real regressions found by testing against paraphrased questions, not arbitrary constants — re-verify against varied phrasings if you touch the scoring.

### Translation: articles and exercise instructions

`src/lib/googleTranslate.ts`'s `translateBatch()` is the shared low-level piece behind both translate features below — it calls Google Translate's free, keyless `translate_a/single` endpoint directly from the browser (unofficial/undocumented, but CORS-enabled and backed by real neural MT, not memory-lookup), with its own retry/concurrency handling. **This is not an LLM/AI translator.** An earlier version called Groq's chat completions API (LLM-based, JSON mode) but proved unreliable in practice — Groq's free-tier daily token budget (100,000 tokens/day, shared across the whole Groq organization regardless of which of this app's Groq keys is used) was exhausted by moderate testing volume alone, and a free crowd-sourced-memory alternative (MyMemory) was tried next but rejected after testing showed its "best match" was sometimes pure garbage — including, in one case, a literal cached error message ("QUERY LENGTH LIMIT EXCEEDED...") served back as if it were a real translation, because its match-ranking has no protection against bad community-submitted data. No API key of any kind is needed for either feature below.

`src/data/indianLanguages.ts` lists 20 of the 22 languages in the Eighth Schedule of the Indian Constitution (India's own official-languages list, not an arbitrary pick) — deliberately no non-Indian languages, and between them these cover the principal language of virtually every state; Bodo and Kashmiri are left out because Google Translate doesn't support either as a target, confirmed by testing all 22 directly against it. `src/components/LanguageSelector.tsx` is the one shared dropdown UI (exports the `ENGLISH` sentinel too) used by every translate feature — each caller owns its own fetch/cache logic (what's being translated differs) but the picker and language list don't.

**Articles** (`ArticleModal.tsx`, language dropdown top-right next to the category badge) translates the open article's title and paragraphs on demand — English is always the default/original. `src/lib/articleTranslate.ts` checks Neon's `article_translations` table first (keyed `(article_id, language_code)`, see `db/schema.sql`) and only calls `translateBatch` on a cache miss, so a given combination only ever hits Google once — every subsequent reader gets an instant cached read.

**Exercise instructions** (`ExerciseModal.tsx`'s "View full guide" popup, and `ExerciseGuide.tsx`'s inline panel on `/exercises` — both share the same layout) translate an exercise's name, description, and numbered steps the same way, via `src/lib/exerciseTranslate.ts` and Neon's `exercise_translations` table (keyed `(exercise_id, language_code)`). Muscle group and difficulty are deliberately never translated — short fixed labels/tags, not prose, same reasoning as `ArticleModal.tsx` leaving its category badge in English. `ExerciseGuide.tsx` keys its local cache by `` `${exerciseId}:${languageCode}` `` rather than just language, since — unlike the two modals, which are fresh component instances per open — it stays mounted while a visitor flips between the pill selector's exercises, so a chosen language stays "sticky" across switches without re-hitting Neon for an already-seen exercise+language pair.

### Legal pages

`src/pages/TermsPage.tsx` (route `/terms`) and `src/pages/PrivacyPolicyPage.tsx` (route `/privacy`) are plain prose pages, linked from the copyright line at the very bottom of `Footer.tsx` — not in `navLinks`, same reasoning as `/profile`/`/app`. Both share `src/components/LegalPageLayout.tsx` (the hero shell — a neutral slate/gray tint in dark mode, unlike every other page's topic-colored dark-mode tint, since legal content isn't tied to a specific feature; light mode uses the same cyan every other page's hero uses, see "Hero and Footer color (light mode)" below) and its `LegalSection`/`LegalList` helpers for consistent heading/paragraph/list styling (no `@tailwindcss/typography` plugin installed, so these are hand-styled rather than `prose` classes). **The content is written to reflect what this app actually does** (Clerk auth, Neon storage, Groq for chat/protein estimation, Google Translate for articles, no real payment processing anywhere) — if a described practice changes, e.g. a new third-party service is added, update the corresponding section rather than leaving it stale.

### Hero and Footer color (light mode)

Every page's hero section (the dark `bg-gray-900` band at the top, each with its own `{/* Hero */}` comment) and the shared `Footer.tsx` use cyan in light mode — `bg-cyan-950` with a `from-cyan-950 via-cyan-900 to-cyan-700` gradient — instead of the near-black gray shown before. **Dark mode is untouched**: every hero's original per-page accent (green/orange/amber/slate, via `dark:` classes) and the Footer's original `bg-gray-900` still render exactly as before. **Home is untouched in both themes** — it has no shared hero section (its hero is `HomeVideoBackground`'s looping video, coded entirely within `HomePage.tsx`, not the `bg-gray-900`-band pattern every other page uses), and `Footer.tsx` checks `path === '/'` from `useRouter()` to skip the cyan treatment and keep Home's footer on the original `bg-gray-900` in either theme, since the Footer component itself is shared and renders on Home too. If a new page is added with the standard hero pattern, give it the same `bg-cyan-950 ... dark:bg-gray-900` / `from-cyan-950 ... dark:from-gray-900 ...` treatment for consistency.

### Footer: QR code, newsletter signup, and the App Coming Soon page

`Footer.tsx` has a band (above the copyright bar) with two things: a QR code linking to `/app`, and a newsletter signup form. `src/components/QRCode.tsx` generates the QR entirely client-side via the `qrcode` npm package (canvas → data URI, no third-party QR-image API call) — the encoded value is an **absolute** URL (`window.location.origin + BASE_URL + 'app'`), not a relative path, since a phone camera scanning it needs a real URL, and it has to resolve correctly under both localhost and the GitHub Pages `/Back-To-Fire/` subpath. `src/pages/AppComingSoonPage.tsx` (route `/app`, not in `navLinks` — reached via the QR scan or its footer link, same "not a marketing nav destination" reasoning as `/profile`) is a plain "App Coming Soon" notice — there is no real app yet, so it deliberately doesn't link to or imply a live Play Store listing.

`src/components/NewsletterForm.tsx` is shared between the Footer band and the App Coming Soon page (`variant="dark"`/`"light"` only changes input styling to fit each background) and both write to the same Neon table, `newsletter_subscribers`, via `src/lib/newsletter.ts` — same browser-direct-to-Neon pattern as `contact.ts`, reusing `VITE_NEON_CONTACT_URL` (no new credential). `email` is `UNIQUE` with `ON CONFLICT DO NOTHING`, so re-subscribing the same address is a silent no-op that still shows the success state, not an error — a visitor has no way to tell "you're already on the list" from "welcome," which is the intended, harmless ambiguity.

### Tools page (`/tools`)

`src/pages/ToolsPage.tsx` hosts three free, no-sign-in-required tools, stacked vertically: `src/components/BmiCalculator.tsx` and `src/components/ProteinCalculator.tsx` (both plain client-side arithmetic, no network calls — extracted out of `ContactPage.tsx`, which used to host them alongside the contact form; they moved here in full along with their state, this file has no lingering references to either) and `src/components/ProteinChatBot.tsx`, a second, separate AI chatbot.

**The protein chatbot is a distinct Groq integration from the main site assistant, on purpose — different job, different key.** `src/lib/proteinChat.ts` takes a free-text description of what the visitor ate and asks Groq (same `llama-3.3-70b-versatile` model) to itemize each food's estimated protein and total it, entirely from the model's own nutritional knowledge — there's no BM25/knowledge-base retrieval step like `groqChat.ts` has, since this isn't answering questions about Born to Fire, it's estimating nutrition from arbitrary user-described food. It authenticates with `VITE_GROQ_PROTEIN_API_KEY`, a **second, separate Groq API key** from `VITE_GROQ_API_KEY` (same "ships to the browser on purpose, no backend to hide it behind" tradeoff as the main chatbot — see `groqChat.ts`'s SECURITY NOTE) so either key can be rotated independently without affecting the other feature. `ProteinChatBot.tsx` mirrors `ChatBot.tsx`'s message-list/history/suggestions structure but — unlike `ChatBot.tsx`, which is body-only and gets its header from `ChatWidget.tsx` — owns its own header/card chrome directly, since it's embedded inline on the page rather than living inside the floating widget.

### Exercise guide (Exercises page)

`src/components/ExerciseGuide.tsx` is a pill selector (all 18 exercises, same tab-strip pattern used elsewhere in the app) over a single "image + numbered steps" panel for whichever exercise is selected — the same layout `ExerciseModal.tsx`'s "View full guide" popup already used, just inline on the page instead of in a modal, and reading straight from `exercise.image`/`exercise.steps` in `src/data/exercises.json` rather than deriving anything. This **replaced** an earlier from-scratch three.js scene (a two-bone IK system posing a rigged `soldier.glb` character in real time, `exerciseVisualizer.ts`/`riggedCharacter.ts`/`ExerciseDemo.tsx`) — removed entirely, along with the `three`/`@types/three` dependencies and the `soldier.glb` asset, since nothing else in the app used three.js once the Home page's flex character was separately replaced by the frame-sequence scrubber below. If a 3D visualizer is ever wanted again, check git history for that implementation rather than rebuilding the IK/rigging work from scratch — it took real effort to get the bone mapping, hand orientation, and camera framing right.

### Home page background video

`src/components/HomeVideoBackground.tsx` is a `position: fixed`, full-viewport layer (`public/videos/home-background.mp4`) sitting behind the entire Home page — every section scrolls over it in normal flow while the video itself never moves, with `object-cover` filling the viewport edge-to-edge and the same dark gradient overlay (`from-gray-900/85 via-gray-900/70 to-gray-900/90`) plus two blurred glow blobs that every other faded-hero treatment on this page uses. It just autoplays on a loop (`muted loop playsInline`, `.play()` called imperatively on mount) — **not** scroll-scrubbed. `prefers-reduced-motion` skips the `.play()` call entirely, leaving the video paused on its first frame.

**This replaced an earlier scroll-scrubbed 240-frame JPEG sequence** (`HomeFrameBackground.tsx` + `src/lib/frameScrub.ts`, a Canvas2D crossfade stepped by whole-page scroll position, ~5.6MB of images in `public/frames/flex-transition/`) — removed entirely, files included, rather than kept as a fallback. The swap traded a scroll-driven "reveal" interaction for a simpler always-playing loop, specifically because scrubbing a `<video>`'s `currentTime` on every scroll event is a known source of stutter (browsers aren't built for frame-precise video seeking the way swapping still canvas images is) — if a scroll-scrubbed effect is ever wanted again, the frame-sequence approach (not video-seeking) is the technique to reach for; check git history for the removed implementation rather than rebuilding it from scratch.

## Auth (Clerk)

Auth is [Clerk](https://clerk.com)'s React SDK (`@clerk/clerk-react`), used entirely client-side — fitting the "no backend" constraint, unlike the Neon/Groq browser calls this isn't a deliberate insecurity, Clerk's publishable key is designed to be public. `ClerkProvider` wraps the app in `src/main.tsx`. Browsing every page works fully signed-out; the only gated actions are the ones that write something — submitting the contact form (`src/pages/ContactPage.tsx`) and enrolling in a program or event (see "Enrollments" above) — all check `useUser()`'s `isSignedIn` and fall back to `openSignIn()` (a modal, via `useClerk()`) instead of a dedicated route, since the app's hand-rolled router (`src/lib/router.tsx`) doesn't integrate with Clerk's routing props. The "Forgot password?" flow is built into Clerk's prebuilt `<SignIn/>`/modal UI automatically whenever email/password is enabled as a sign-in strategy in the Clerk Dashboard — no app code implements it. `Navbar.tsx`'s `<UserButton>` adds one custom menu item ("My Profile" → `/profile`) via `<UserButton.MenuItems><UserButton.Action .../></UserButton.MenuItems>`, Clerk's supported custom-action API — not `<UserButton.Link href=.../>`, since a raw `href` would bypass the SPA router and force a full page reload.
